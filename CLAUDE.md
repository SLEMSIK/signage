# Signage — система управления контентом на экранах

## Цель

Система digital signage для локальной сети учреждения. Есть сервер (Docker-контейнер на Node.js в VM Ubuntu на Proxmox) и плееры на экранах (Windows OPS + браузер в kiosk-режиме). Через веб-админку можно загружать контент, собирать плейлисты, назначать их на экраны и группы, переключать контент вручную и задавать расписание по дням недели и времени.

Экраны на старте: 2 ТВ в холле и 1 экран на 3 этаже. Система должна легко расширяться до N экранов.

## Требования (зафиксированы с заказчиком)

- **Экраны:** горизонтальные, 1920×1080. Любой контент масштабируется под эту сцену.
- **Плееры:** Windows на OPS. Плеер — веб-страница, открытая в Microsoft Edge (или Chrome) в kiosk-режиме. Скрипты установки киоска входят в проект.
- **Звука нет:** видео всегда воспроизводится muted.
- **Независимость экранов:** каждый экран показывает своё. Через группы можно показывать одно и то же, в том числе синхронно.
- **Типы контента:** изображения (jpg, png, webp, gif), видео (mp4/h264, webm) — лёгкие заставки, HTML одним файлом и HTML-пакет в zip (index.html + ассеты).
- **Интернет есть только у сервера.** Экраны в интернет не ходят. HTML-контент получает внешние данные через прокси-эндпоинт сервера.
- **Плейлисты:** упорядоченный список элементов, у каждого своя длительность. Плейлист проигрывается по кругу.
- **Расписание:** по дням недели и времени. Вне расписания экран показывает чёрный экран. Физически экран не выключается.
- **Ручное переключение:** оператор может временно назначить экрану или группе другой плейлист либо чёрный экран.
- **Экстренная кнопка «на все экраны» не нужна.**
- **Роли:** `admin` и `operator`. Пользователи и пароли задаются в конфиге, регистрации через UI нет.
- **Доступ** только из локальной сети. Внешнего доступа нет.
- **Хранилище медиа:** сетевой диск SMB (сейчас `\\10.33.44.5`). Адрес, шара и учётные данные задаются в конфиге.
- **Язык UI:** русский. Часовой пояс: `Europe/Moscow` (задаётся в конфиге).

## Стек

- Node.js 22 LTS, TypeScript (strict)
- Сервер: Fastify, `@fastify/websocket`, `@fastify/static`, `@fastify/multipart`, `@fastify/cookie`
- БД: SQLite (`better-sqlite3`) + Drizzle ORM, миграции
- Валидация: zod (конфиг, API)
- Пароли: bcrypt. Сессии: подписанная cookie, httpOnly
- Админка: React + Vite + TypeScript, собирается в статику и раздаётся сервером
- Плеер: vanilla TypeScript, минимум зависимостей, отдельная сборка Vite
- Тесты: vitest. Обязательно покрыть движок расписания
- Распаковка zip: `yauzl` или `adm-zip` с защитой от zip-slip
- Монорепо: npm workspaces

## Конфигурация

`config/config.yaml` монтируется в контейнер read-only:

```yaml
server:
  port: 8080
  publicUrl: "http://10.33.44.20:8080"   # адрес, по которому плееры видят сервер
  timezone: "Europe/Moscow"
  sessionSecret: "change-me"
  allowedNetworks: ["10.0.0.0/8", "192.168.0.0/16", "172.16.0.0/12"]  # остальным 403

users:
  - login: admin
    role: admin
    passwordHash: "$2b$10$..."   # сгенерировать: npm run hash-password
  - login: operator
    role: operator
    passwordHash: "$2b$10$..."

storage:
  mediaPath: /data/smb/share      # SMB внутри контейнера (монтирует хост)
  dbPath: /data/db/signage.sqlite # ЛОКАЛЬНЫЙ volume, не SMB
  backupPath: /data/smb/share/_backup # куда класть ежедневный бэкап БД
  maxUploadMb: 500

proxy:
  allowlist:                      # домены, которые HTML-контент может запрашивать через сервер
    - "api.open-meteo.com"
    - "www.cbr-xml-daily.ru"
  cacheTtlSec: 300

player:
  heartbeatSec: 15
  offlineAfterSec: 45
  defaultImageDurationSec: 10
  defaultHtmlDurationSec: 30
```

SMB монтируется **на хосте** скриптом `deploy/setup-smb.sh` (fstab с `nofail` + таймер `signage-smb-remount` раз в минуту), а в контейнер пробрасывается родительский каталог с `propagation: rslave`. Так контейнер стартует и без SMB, а шара, смонтированная позже, появляется в нём без перезапуска. Параметры SMB лежат в `.env`; смена адреса — правка `.env` и повторный запуск скрипта:

```yaml
# docker-compose.yml (фрагмент)
volumes:
  - type: bind
    source: ${SMB_ROOT:-/srv/signage-smb}   # шара смонтирована в $SMB_ROOT/share
    target: /data/smb                       # storage.mediaPath: /data/smb/share
    bind: { propagation: rslave }
  - local_media:/data/local-media           # диск VM: резерв и копия медиатеки
  - db:/data/db
```

В пустом каталоге точки монтирования лежит метка `.NOT-MOUNTED`. Если сервер её видит, значит SMB не смонтирован.

**Важно:** SQLite нельзя держать на SMB, там ломаются блокировки. БД хранится на локальном volume `db`. Раз в сутки и при старте делается бэкап (`VACUUM INTO`) в `storage.backupPath` на SMB. Ротация — 14 копий.

Если SMB недоступен, сервер не падает, плееры продолжают играть из своего кэша.

**Работа с диска VM (приоритет — SMB).** При `storage.localMirror: true` сервер держит на диске VM копию всей медиатеки (`media.mirrored`) и, пока SMB недоступен, отдаёт файлы из неё. Пока SMB недоступен, новые загрузки сохраняются в `storage.localFallbackPath` (Docker-volume `local_media` на диске VM). У медиафайла в БД есть поле `location` (`primary` — SMB, `local` — диск VM); относительный путь одинаков в обоих местах, поэтому URL не меняются. После каждой успешной проверки SMB (раз в 30 с и в `/health`) сервер переносит локальные файлы на SMB: копия во временный путь → проверка (sha256 для файла, состав и размеры для zip-пакета) → rename → `location = primary` → удаление локальной копии. Если на диске VM свободно меньше `storage.localMinFreeMb`, загрузка отклоняется. В админке при этом жёлтый баннер «Сетевое хранилище недоступно — файлы сохраняются на диск сервера (ждут переноса: N)». Если `localFallbackPath: null`, резерв выключен и загрузка при недоступном SMB блокируется (красный баннер).

## Модель данных

- `groups` — id, name
- `screens` — id, name, group_id (nullable), token_hash, pairing_code, status, last_seen_at, current_item (json), fit_default (`contain`|`cover`), sync_mode (bool, берётся из группы), created_at
- `media` — id, type (`image`|`video`|`html`|`html_zip`), title, location (`primary`|`local`), rel_path (относительно корня хранилища), entry (для zip — путь к index.html), size, sha256, duration_sec (для видео — автоматически через ffprobe; иначе null), thumb_path, created_at, created_by
- `playlists` — id, name, created_at, updated_at
- `playlist_items` — id, playlist_id, media_id, position, duration_sec (null — по умолчанию; для видео — длина ролика), fit (`contain`|`cover`|`stretch`), transition (`none`|`fade`)
- `schedules` — id, target_type (`screen`|`group`), target_id, playlist_id (null — чёрный экран), days (битовая маска Пн..Вс), start_time `HH:MM`, end_time `HH:MM` (поддержать переход через полночь: 22:00–02:00), priority (int), enabled
- `overrides` — id, target_type, target_id, playlist_id (null — чёрный экран), until (timestamp или null — до отмены), created_by, created_at
- `audit_log` — id, user, action, entity, entity_id, payload (json), at

## Движок расписания (ядро системы)

Чистая функция `resolve(screen, now, data) → { playlistId | null, source, validUntil }`. Порядок приоритета:

1. Активный override на экран
2. Активный override на группу экрана
3. Расписание экрана, подходящее под now. При пересечении выигрывает больший priority, при равенстве — более позднее по start_time
4. Расписание группы
5. Иначе `null` — чёрный экран

`validUntil` — ближайший момент, когда результат может измениться (граница любого расписания или истечение override). Сервер держит таймер на ближайший `validUntil` по всем экранам и при срабатывании пересчитывает и пушит изменения. Плюс страховочный пересчёт раз в минуту и при любом изменении данных.

Учитывать `server.timezone`, а не таймзону контейнера. Тесты: пересечения, переход через полночь, переход между днями недели, override с истечением, приоритеты, группа против экрана.

## Синхронный показ в группе

У группы есть флаг `syncPlayback`. Если он включён, позиция в плейлисте вычисляется детерминированно от общего времени: `(serverNow - playlistEpoch) mod totalDuration`, где `playlistEpoch` — момент начала назначения. Плееры корректируют часы по серверу (offset считается из ping/pong по WS). Тогда экраны в группе показывают один и тот же слайд одновременно. Если флаг выключен, каждый плеер играет плейлист с начала независимо.

## Протокол плеера (WebSocket `/ws/player`)

Все сообщения описаны zod-схемами в `packages/shared`.

Плеер → сервер:
- `hello { token? }` — при подключении
- `heartbeat { currentItemId, playlistId, cacheStatus, viewport, uptime }`
- `pong { t }`
- `error { message, mediaId? }`

Сервер → плеер:
- `pairing { code }` — плеер не зарегистрирован. Показать крупный 6-значный код на экране
- `paired { token, screenId, name }` — сохранить token в localStorage
- `state { playlist: { id, items: [{ mediaId, url, type, durationSec, fit, transition }] } | null, syncEpoch?, version }`
- `ping { t }`
- `reload` — перезагрузить страницу (кнопка в админке)
- `identify` — на 10 секунд показать имя экрана поверх контента (кнопка в админке)

Админка подписывается на `/api/admin/ws` (по сессии; путь под `/api/admin`, потому что cookie сессии ограничена этим путём) и получает статусы экранов в реальном времени.

## Регистрация экрана

1. В киоске открывается `http://<server>/player`.
2. Без токена плеер получает код и показывает его на весь экран.
3. Админ в разделе «Экраны» нажимает «Добавить», вводит код, имя и группу.
4. Сервер выдаёт токен, плеер его сохраняет. При повторных запусках код больше не нужен.
5. Сброс: админ удаляет экран — токен инвалидируется, плеер снова показывает код.

## Плеер

- Сцена фиксированная, 1920×1080, и масштабируется под окно через `transform: scale()` с letterbox. Фон всегда чёрный.
- Изображения: `<img>` с `object-fit` по настройке элемента.
- Видео: `<video muted autoplay playsinline>`. Длительность элемента по умолчанию равна длине ролика. Если видео не стартовало за 5 секунд — пропустить элемент и отправить `error`.
- HTML и zip: `<iframe sandbox="allow-scripts allow-same-origin">` размером 1920×1080 внутри сцены. Отдаются с отдельного пути `/content/<mediaId>/...`.
- Двойная буферизация: следующий элемент загружается в скрытый слой заранее, переход — мгновенный или fade. Чёрных пауз между элементами быть не должно.
- `state null` — чёрный экран. Курсор скрыт всегда (`cursor: none`).
- Если WS отвалился — продолжать играть текущий плейлист и переподключаться с экспоненциальной задержкой (до 30 с).
- Защита от утечек памяти: раз в сутки в 04:00 — тихий `location.reload()` на границе элемента.

### Офлайн-кэш (Service Worker)

- SW кэширует оболочку плеера и все URL текущего и последнего плейлиста (Cache API). По `state` докачивает новое и удаляет неиспользуемое.
- Сервер отдаёт медиа с ETag на основе sha256 и `Cache-Control: immutable` для версионированных URL (`/media/<id>?v=<sha8>`).
- Последний `state` хранится в localStorage. При холодном старте без сервера плеер играет его, но расписание без сервера не пересчитывается.
- **Важно:** Service Worker и Cache API работают только в secure context. Сервер доступен по http и IP, поэтому киоск запускается с флагом `--unsafely-treat-insecure-origin-as-secure=<publicUrl>` (это прописано в `install.ps1`). Плеер обязан работать и без SW: проверять `'serviceWorker' in navigator`, а при отсутствии деградировать до обычной загрузки.

## Внешние данные для HTML-контента

Экраны не имеют интернета, поэтому HTML-контент ходит через сервер:

`GET /api/proxy?url=<encoded>` — только для доменов из `proxy.allowlist`, только GET, кэш на `cacheTtlSec`. Если внешний источник недоступен — отдаётся последний успешный ответ. Эндпоинт доступен с токеном плеера или с сессией.

В каждый HTML-контент сервер инжектит маленький скрипт `window.signage = { fetch(url) }`, который оборачивает прокси. В `docs/` нужен пример HTML-виджета «часы + погода + курс ЦБ».

Ограничение для авторов HTML: все библиотеки (шрифты, JS) должны лежать внутри zip. CDN с экранов недоступны. В админке при загрузке zip — предупреждение, если в index.html найдены внешние `http(s)://` ссылки на скрипты, стили или шрифты.

## Медиатека

- Загрузка drag-n-drop, несколько файлов сразу, прогресс-бар.
- Zip: проверка на zip-slip, лимит размера после распаковки, обязательно `index.html` (в корне или в единственной папке верхнего уровня).
- Превью: картинки — ресайз (sharp), видео — кадр через ffmpeg (в образ поставить ffmpeg), HTML — заглушка с иконкой (опционально — скриншот через playwright, отдельная задача на потом).
- Удаление медиа, используемого в плейлистах: предупреждение со списком плейлистов.
- Структура на SMB: `media/<yyyy>/<mm>/<uuid>.<ext>`, zip распаковывается в `media/html/<uuid>/`.

## Админка (разделы)

1. **Дашборд** — карточки экранов: онлайн/офлайн, что играет сейчас, источник (расписание, override, по умолчанию), когда смена. Быстрые действия: «Переключить», «Чёрный экран», «Вернуть расписание», «Идентифицировать», «Перезагрузить».
2. **Экраны и группы** — регистрация по коду, имя, группа, fit по умолчанию, флаг синхронизации у группы.
3. **Медиатека** — сетка с превью, фильтр по типу, поиск.
4. **Плейлисты** — редактор с drag-n-drop сортировкой, длительность и fit для каждого элемента, предпросмотр плейлиста в окне 16:9.
5. **Расписание** — недельная сетка (Пн–Вс × часы) для выбранного экрана или группы с цветными блоками плейлистов. Создание блока выделением мышью. Видно, что унаследовано от группы.
6. **Журнал** — audit log с фильтрами.
7. **Настройки** (admin) — статус SMB, бэкап и восстановление БД, версия.

Ручное переключение: выбрать экраны или группу → плейлист или «чёрный экран» → срок: «до следующей смены по расписанию», «на N часов», «до отмены».

## Киоск для Windows (`kiosk/`)

Используем Microsoft Edge, он уже есть в Windows. Отдельный браузер ставить не нужно.

`install.ps1 -ServerUrl http://10.33.44.20:8080` (запуск от администратора):
- создаёт отдельный профиль Edge `C:\Signage\EdgeProfile`;
- создаёт задачу планировщика «при входе пользователя», которая запускает `watchdog.ps1`;
- `watchdog.ps1` запускает Edge и перезапускает его, если процесс завершился (проверка каждые 10 с). Строка запуска:
  ```
  msedge.exe --kiosk "<ServerUrl>/player" --edge-kiosk-type=fullscreen
    --user-data-dir=C:\Signage\EdgeProfile --no-first-run --noerrdialogs
    --disable-session-crashed-bubble --disable-features=Translate
    --autoplay-policy=no-user-gesture-required
    --unsafely-treat-insecure-origin-as-secure=<ServerUrl>
  ```
- отключает сон и гашение экрана (`powercfg /change monitor-timeout-ac 0`, `standby-timeout-ac 0`);
- отключает уведомления и подсказки Windows, где возможно;
- выставляет активные часы Windows Update, чтобы перезагрузки шли ночью;
- в `README.md` — инструкция по автологину (Sysinternals Autologon), локальному пользователю без прав админа и проверке.

`uninstall.ps1` откатывает всё обратно. Выход из киоска для обслуживания — Alt+F4 при остановленной задаче. Описать это в README.

## Безопасность

- Middleware отклоняет запросы не из `allowedNetworks` (с учётом `trustProxy`, если будет reverse proxy).
- Rate limit на логин, блокировка на 5 минут после 10 неудачных попыток.
- Токен плеера даёт доступ только к `/player`, `/ws/player`, `/media`, `/content`, `/api/proxy` и не открывает админ-API.
- HTML-контент отдаётся с отдельного пути и не получает cookie админки (cookie с `path=/admin` и `/api/admin`).
- Без секретов в образе: всё передаётся через config и `.env`.

## Деплой (`docs/deploy.md`)

1. Proxmox → VM Ubuntu Server 24.04, 2 vCPU, 2–4 GB RAM, 20 GB диск.
2. Установить Docker Engine + compose plugin и `cifs-utils`.
3. Склонировать репозиторий, заполнить `.env` (SMB_HOST, SMB_SHARE, SMB_USER, SMB_PASSWORD) и `config/config.yaml`.
4. `docker compose up -d`. Healthcheck: `GET /health` (проверяет БД и доступность mediaPath).
5. `restart: unless-stopped`. Логи — в stdout в формате JSON (pino).
6. Описать миграцию VM при отказе узла (Proxmox HA) и восстановление БД из бэкапа на SMB.

Dockerfile: multi-stage на node:22-alpine (или bookworm-slim, если sharp/ffmpeg так проще), сборка admin и player, финальный образ без devDependencies, запуск не от root.

## Этапы разработки

Делать по порядку. После каждого этапа — рабочее состояние и коммит.

1. **Каркас:** монорепо, TypeScript, Fastify, загрузка конфига (zod), SQLite + миграции, `/health`, Dockerfile и compose с SMB-volume.
2. **Авторизация:** логин по пользователям из конфига, роли, сессии, фильтр сетей, CLI `hash-password`, каркас админки (логин и пустые разделы).
3. **Медиатека:** загрузка, zip с проверками, превью, раздача `/media` и `/content` с ETag.
4. **Экраны:** WS-хаб, pairing по коду, токены, статусы и heartbeat, дашборд онлайн/офлайн.
5. **Плеер v1:** сцена 1920×1080, показ одиночного элемента всех типов, чёрный экран.
6. **Плейлисты:** CRUD и редактор, проигрывание в плеере с двойной буферизацией и fade.
7. **Расписание:** движок с тестами, CRUD, недельная сетка, таймеры пересчёта.
8. **Ручные переключения (overrides)** и быстрые действия на дашборде.
9. **Группы и синхронный показ.**
10. **Офлайн:** Service Worker, кэш, last state, переподключения.
11. **Прокси внешних данных** + инжект `window.signage` + пример виджета.
12. **Киоск-скрипты для Windows.**
13. **Журнал, бэкапы БД, баннер недоступности SMB.**
14. **Документация деплоя**, финальная проверка на реальном экране.

## Соглашения

- Код и идентификаторы — на английском, UI и документация — на русском.
- Время в БД — UTC (ISO или epoch ms). Время расписания (`HH:MM`) — в `server.timezone`.
- Пути в медиатеке хранятся относительными, чтобы смена SMB-адреса не ломала данные.
- Перед коммитом: `npm run lint`, `npm run typecheck`, `npm test`.
